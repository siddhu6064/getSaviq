## Scope calls (read before reviewing the diffs)

- **#12 Multi-currency** is scoped to **display/formatting only**: a per-profile
  currency preference that changes the symbol/format everywhere (`formatCurrency`
  currently hardcodes USD at every call site despite already accepting a currency
  param). This does **not** add FX conversion or mixed-currency-per-transaction —
  that's a materially bigger feature (rate API, conversion pipeline) and belongs in
  the v2 "real" multi-currency item, not this quick-win pass.
- **#6 Cash-flow forecast** is scoped to a **30-day day-by-day projected-balance
  list** (current balance + upcoming bill due dates + recurring expenses), not a
  full custom calendar grid. Delivers the actual value (see a shortfall coming)
  without the extra UI-build cost of a grid component.
- **#7 CSV import** round-trips the existing export format exactly (`Date, Type,
Description, Amount, Category, Payment Method, Merchant, Notes`), resolving
  category/payment-method names to IDs (creating them if missing, same as manual
  entry would).

## Post-launch additions (from app-store competitor sweep, 2026-09-10)

Cross-checked Forbes/CNBC/ripenapps "best expense tracker" roundups against
actual SAVIQ code (not just the original gap analysis). Two genuinely new,
self-contained gaps surfaced and were shipped same-day:

- [x] 5. **Voice/NL quick-add.** `POST /ai/parse-expense-text` (same
     graceful-fallback pattern as `/scan-receipt` — deterministic `{type:
"expense", amount: null, category_suggestion: "Other", ...}` fallback
     when the model call fails, verified live via curl with no
     `OPENAI_API_KEY` set). **Scope call:** true on-device speech capture
     needs a native STT module (`expo-speech-recognition` or similar) — same
     native-build-risk class as the widgets item deferred to v2, so it's
     explicitly out of scope here. Instead: web gets a real in-browser mic via
     the native `SpeechRecognition`/`webkitSpeechRecognition` API (zero new
     dependency, feature-detected, hidden when unsupported); mobile gets a
     "Quick Add" text field that the OS keyboard's own dictation mic already
     fills (also zero new native dependency). Both paths hit the same
     text-parsing endpoint. 6 new pytest tests, live-verified end to end in
     browser (typed text → parsed → form fields prefilled).
- [x] 6. **Refund tracking.** `POST /expenses/{id}/refund` creates a linked
     income transaction (`refund_for_expense_id`), reusing `create_expense`
     internally rather than duplicating budget/bill-match logic (refunds are
     income, so those alerts correctly don't fire). `GET
/expenses/{id}/refunds` lists refunds for the "already refunded" total.
     6 new pytest tests (full refund, partial refund, 404s, ownership
     scoping, refund listing). Web: refund icon on each expense row (table +
     mobile-card view) opens a `RefundModal` prefilled with the remaining
     unrefunded amount. Mobile: "Record Refund" button in the transaction
     detail sheet, refunded total shown as a detail row once any refund
     exists. Live-verified end to end on web (created $80 expense, recorded a
     $30 partial refund, confirmed the linked +$30.00 income row appeared).

Considered and explicitly **not** added (until asked): mileage tracking,
tax-deduction tagging, Zillow-style home-value auto-sync — all niche for a
personal (non-business) tracker, or belong in the same external-API-dependency
class as bank sync.

- [x] 7. **Trip budgets.** New `TripBudget` model/router (`trip_budgets.py`),
     deliberately kept separate from the existing recurring `Budget` model
     rather than overloading it — a trip is a one-off, named, bounded date
     range, not a calendar-period-renewing cap, and retrofitting "custom"
     periods into `Budget`'s period logic would have risked the existing
     (well-tested) weekly/monthly/yearly budgets. `POST/GET/PUT/DELETE
     /trip-budgets`, spend computed as a direct sum over expenses in
     `[start_date, end_date]` (optionally scoped to one category), not a
     Mongo `$group` aggregation — deliberately simple since trip-scoped
     expense counts are small. 11 new pytest tests (date-range scoping,
     category scoping, over-budget flag, ownership, date-order validation on
     create and update). Web: new "Trip Budgets" section on the Budgets page
     (list + add/edit modal + delete confirm), live-verified end to end
     (created "Japan Trip" $2,000 budget, confirmed date range and days-left
     render correctly). Mobile: matching section on `budgets.tsx`, dates
     entered as plain `YYYY-MM-DD` text fields rather than a date-picker
     component — the only native date-picker library in the project
     (`@react-native-community/datetimepicker`) is installed but unused
     anywhere in the app, and first-time-wiring an unverified native module
     right now repeats exactly the risk class already deferred for widgets in
     V2_PLAN.md; `tsc --noEmit` clean.

Backend: 220/220 pytest passing after all three additions.
